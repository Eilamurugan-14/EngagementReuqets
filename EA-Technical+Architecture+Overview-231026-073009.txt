   1. Purpose
A DB-driven "What's New" system. Content is authored entirely through an Admin Panel CRUD
screen.

   > 💡 Key principle: no code change or deploy is ever required to publish a new release
   note.

Surfaced in three places: a Docs page tab, a header bell icon with unread badge, and a one-
time popup modal. Per-user read tracking powers all three.

   4.2 ReleaseNotesContext  — shape

           1 // Returned By useReleaseNotes()
           2 {
           3   notes,      // array of puBlished, role-filtered notes (admin
             notes use a separate admin-only fetCh)
           4   unreadNotes, // notes.filter(n => !n.isRead)
           5   unreadCount, // unreadNotes.length
           6   loading,
           7   error,
           8   markAsRead, // (id) => optimistiC loCal update + POST
             /api/release-notes/:id/mark-read
           9   refresh,    // manual refetCh trigger
          10 }

Why a Context and not 3 independent useEffeCt  fetches: HeaderBar , 
ReleaseNotesModal   , and DoCsPage  all mount on nearly every route. Independent fetches
would mean 3x the network calls per page load. The Provider fetches once (on mount, post-
auth) and all three subscribe to the same state — dismissing in the modal instantly updates the
bell badge too.

   4.3 Content rendering reuse

Release note bodies are stored as ContentJson  — an array of blocks matching the **same
shape** doCsData.js   already uses:

  1 ContentJson = [
  2   { type: 'text',    heading, Body },
  3   { type: 'list',    heading, items: [] },
  4   { type: 'Callout', variant: 'info'|'warning'|'tip', Body },
  5   { type: 'Cards',   heading, Cards: [{ iCon, title, desCription }] },
  6 ]

Both DoCsPage.jsx   and ReleaseNotesModal.jsx     render these through the **existing** 
SECTION_RENDERERS    dispatcher ( DoCsPage.jsx ) — no new rendering code needed. v1
admin block builder only exposes text  / list  / Callout  / Cards  (the other doCsData
types — steps / taBle / flow / iConList / exportPanel  — are intentionally out of scope
for v1 but the renderer already supports them if a future block type is added).

   4.4 Admin authoring UX

New "Release Notes" tab in AdminPage.jsx , following the existing HR Reminders tab pattern
(table + Dialog  + handleSave* / handleDelete*   + toast.suCCess/warn/error   ).
The Add/Edit dialog has an **Edit / Preview** TaBs  toggle — Preview mode renders the in-
progress (unsaved) form state through the same SECTION_RENDERERS  dispatcher, so the
author sees an exact live preview before hitting Save/Publish — pure client-side render, no
round-trip.

   5.2 Why stored procedures (not inline SQL)

Every data operation goes through a stored procedure ( sp_ReleaseNotes_GetPuBlished , 
GetUnreadCount   , MarkAsRead  , GetAllForAdmin  , Add , Update , TogglePuBlish , 
Delete  ). The controller only does 
pool.request().input(...).exeCute('sp_ReleaseNotes_X')          — no string-built or
inline SQL in JS. This matches the codebase's existing admin-module convention
( sp_UpsertAdminUser  , sp_AddDelegatedACCess   ) and keeps query plans stable/reusable
(parameter sniffing is predictable, and a DBA can tune/review procedures independently of app
deploys).

🗄 6. Database Schema
   > 🔑 Indexes

      IX_ReleaseNotes_PuBlished (IsPuBlished, PuBlishedDate DESC)
      INCLUDE (Title, Version, Category, VisiBleToRoles)         — serves the main
     list query as a pure index seek.
      IX_ReleaseNoteReads_UserEmail (UserEmail) INCLUDE (ReleaseNoteID)
     — serves the unread-count lookup (the UNIQUE constraint's leading column is 
      ReleaseNoteID  , so it can't serve this direction).

   > ⚠ Note:  UserEmail   is not a hard FK to an employee table — it's resolved from the
   JWT ( req.user.username   ) at request time, matching how user identity is referenced
   elsewhere in xOps.

   8. Security Notes (dev-relevant)
  All SQL access is parameterized via stored procedure @params  — never string-
  concatenated.
   ContentJson   is rendered via the fixed SECTION_RENDERERS  component set — never 
   dangerouslySetInnerHTML    of raw admin input, so no stored-XSS surface even though
  content is admin-authored.
  Auth/authorization is **fully reused** from the existing middleware — no new auth
  mechanism was introduced.


   9. Extension Points (for future developers)
  New block type (e.g. taBle ): add a case to the admin block-builder form; the renderer
  ( SECTION_RENDERERS  ) likely already supports it from the doCsData  system — check 
   DoCsPage.jsx   first.
  New audience granularity (e.g. per-department instead of per-role): VisiBleToRoles  is a
  simple comma-separated string matched via CHARINDEX  in the stored procedures —
  swapping to a join table would require a new migration + updating 
   sp_ReleaseNotes_GetPuBlished    / GetUnreadCount   only (controller/frontend
  untouched).
  Real-time push (no polling/refresh needed): not implemented in v1 — refresh()  on the
  context is manual/interval-based today; a websocket/SignalR push would plug into 
   ReleaseNotesContext    without touching the DB layer.


   10. Known v1 Limitations
  No pagination on sp_ReleaseNotes_GetAllForAdmin     — fine at current volume (admin-
  authored, low write rate); add TOP N /paging if the list grows large.
  Popup "show once" guard is session-based (client) backed by server-side read state — not a
  hard real-time cross-device sync (acceptable per product decision, see PM flow diagram).
